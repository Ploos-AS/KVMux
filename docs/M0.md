# KVMux M0 — architecture and control plane

## Objective

M0 establishes the KVMux software and hardware contracts before physical multiport hardware is committed.

The milestone is successful when KVMux can model and simulate the complete lifecycle of several managed nodes, including power cycling and OS reinstallation through virtual media.

## Product assumptions

Initial hardware target:

- 8 managed node ports
- one management computer
- shared or switched video resources
- USB HID switching
- virtual USB mass-storage capability
- UART available for every node
- independent power/reset control for every node

Not every node needs video capture simultaneously. Serial and power management should remain available for all ports even when video resources are shared.

## Managed-port capabilities

A port may advertise capabilities independently:

- `video`
- `hid`
- `serial`
- `power`
- `reset`
- `virtual_media`
- `power_telemetry`

This allows lower-cost configurations where some ports provide serial + power only.

## Node model

Minimum node state:

```text
id
name
enabled
capabilities[]
power_state
health
serial_state
video_state
media_state
attached_image
provision_state
last_error
```

### Power states

```text
unknown
off
powering_on
on
powering_off
cycling
fault
```

Power cycle should be an explicit operation rather than an alias for reset.

Default sequence:

1. request power off
2. confirm or wait for power-down
3. enforce configurable off interval
4. request power on
5. report result

A later backend may implement hard cut, soft shutdown, USB-C PD control, relay/MOSFET switching or external managed-PDU control.

## Reset

Reset is independent from power cycle.

Backends may support:

- target reset pin
- simulated reset
- USB-controlled reset hardware
- motherboard/front-panel reset interface

## Virtual media

Virtual media is a first-class KVMux subsystem.

The host should be able to present storage to a selected node as USB mass storage. Images may be:

- ISO
- raw disk image
- installer image
- recovery image
- small utility image

Image metadata should include at minimum:

```text
id
name
path
size
sha256
media_type
read_only
architecture
platform
notes
```

Images should be read-only by default when exposed to a target.

## OS imaging / reinstall

Provisioning is intentionally separated from simple media attachment.

A provisioning job can perform a sequence such as:

1. validate requested image
2. reserve node
3. stop workloads if integration exists
4. power node off
5. attach image
6. configure boot strategy
7. power node on
8. monitor UART/video
9. wait for installer/reimage completion
10. detach image
11. reboot or power-cycle
12. verify expected boot/health condition
13. release node

M0 simulates this state machine. Later milestones bind it to real hardware.

### SBC-specific provisioning

KVMux should not assume every SBC boots from USB in the same way.

Future platform backends may support:

- USB installer media
- USB boot disks
- removable SD imaging
- eMMC provisioning
- network boot
- recovery-button/GPIO boot modes
- board-specific boot selector GPIO

This capability belongs behind a platform abstraction rather than being hard-coded into the generic API.

## API sketch

### Inventory

```text
GET /api/v1/nodes
GET /api/v1/nodes/{id}
```

### Power

```text
POST /api/v1/nodes/{id}/power/on
POST /api/v1/nodes/{id}/power/off
POST /api/v1/nodes/{id}/power/cycle
POST /api/v1/nodes/{id}/reset
```

### Images and media

```text
GET  /api/v1/images
POST /api/v1/images
GET  /api/v1/images/{id}

POST /api/v1/nodes/{id}/media/attach
POST /api/v1/nodes/{id}/media/detach
```

Example media request:

```json
{
  "image": "debian-arm64",
  "read_only": true
}
```

### Provisioning

```text
POST /api/v1/nodes/{id}/provision
GET  /api/v1/jobs/{job_id}
```

Example:

```json
{
  "image": "debian-arm64",
  "strategy": "virtual-media",
  "power_cycle": true
}
```

Provisioning must be asynchronous at the API/job level even though the KVMux service itself owns and executes the operation.

## Hardware abstraction

M0 uses explicit interfaces so simulator and physical hardware can coexist.

Suggested logical interfaces:

```text
power_backend
reset_backend
serial_backend
video_backend
hid_backend
media_backend
telemetry_backend
platform_backend
```

A node configuration maps each capability to a concrete backend instance/channel.

## Simulator

The simulator should be able to model at least eight nodes.

It should support fault injection including:

- node fails to power on
- node ignores reset
- media attach failure
- serial timeout
- installer timeout
- unhealthy boot after provisioning

This lets API and automation behaviour be tested before PCB hardware exists.

## Safety requirements

Power control needs conservative defaults:

- prevent accidental simultaneous destructive operations
- configurable minimum off-time
- idempotent on/off requests
- explicit force option for hard cut
- operation logging
- authentication/authorization before network deployment

Provisioning should require an explicit target node and image. Bulk reinstall must never be the accidental default.

## M0 exit criteria

M0 is complete when:

- 8 simulated nodes can be configured
- node state is queryable
- simulated power on/off/cycle works
- simulated reset works
- images can be registered
- virtual media can be attached/detached
- a simulated provisioning job completes end-to-end
- fault cases are represented and testable
- API behaviour is documented
- physical backend contracts are stable enough to start M1
